# QMIX для адаптивного управления ресурсами гетерогенных IoT-систем

Это воспроизводимая экспериментальная реализация для статьи в журнал «Вестник ВГУ. Серия: Системный анализ и информационные технологии».

## Исследование структурированной адаптации QMIX

В `qmix_aiot/improved_study.py` исследуются два предметных дополнения QMIX:

1. **Обязательное назначение** — если хотя бы один периферийный узел удовлетворяет маске допустимости, действие «отклонить задачу» недоступно. Оно остаётся единственным действием при отсутствии допустимого направления.
2. **Общая сеть оценки кандидатов** — вместо единого линейного слоя с `k+1` выходами для каждого кандидата применяется разделяемая нейросетевая оценка его ресурсов, очереди, сетевого канала и относительного расположения. Локальная история кодируется GRU; централизованный QMIX-смеситель не изменён.

Основные методы: `structured_qmix`, `work_conserving_qmix` (только первый компонент), `structured_no_public` (без числовых объявлений), `structured_optional_reject` (отключено первое дополнение). Сравнение дополнено контрольными моделями `adapted_qmix`, `vanilla_qmix`, `iql`, `no_public`, `no_gru`, `no_fairness`, `no_energy` и эвристиками `greedy`, `round_robin`. Полный эксперимент включает по пять независимых обучений, срезы 55/110 эпизодов, восемь новых контрольных потоков с семенами 4000–4007 и десять нагрузочных режимов. Экспериментальные потоки с семенами 3000–3002 применялись только для предварительной технической проверки.

Синтетические данные не являются реальными измерениями на IoT-стенде; энергетическая переменная не измерена в джоулях.

## Зависимость QMIX от нагрузки

В новом исследовании локальные наблюдения дополнены оценками исходящих сетевых соединений. Этим устранено
различие доступной информации между обучаемым диспетчером и Greedy.

Новая постановка исследует:

1. Четыре стационарные интенсивности поступлений на устройство:
   `0.06`, `0.12`, `0.24`, `0.36` задачи/с (примерная относительная загрузка
   до учёта ожидания и задержек: `0.164`, `0.329`, `0.657`, `0.986`).
2. Пиковые поступления, отказы узлов и неоднородные ресурсы при двух
   контрольных интенсивностях: всего десять режимов.
3. Пять независимых обучающих инициализаций и два среза бюджета обучения:
   после 55 и 110 эпизодов; восемь отложенных проверочных потоков на каждую
   комбинацию модели и режима.
4. Четыре независимые абляции: `no_public` (без числовых объявлений соседей),
   `no_gru` (без рекуррентного слоя), `no_fairness` (без штрафа за
   неравномерность) и `no_energy` (без суррогатного штрафа затрат).
5. Альтернативы `vanilla_qmix`, `iql`, `greedy`, `round_robin`.

Обучение можно разделить на независимые пакеты: сначала основные методы,
затем три дополнительные абляции, после чего объединить исходные записи
командой `python -m qmix_aiot.merge_regime_ablations --primary
results_regime2026 --auxiliary results_regime_ablations`. Объединяющая команда
проверяет совместимость всех параметров, повторяющиеся записи, число
испытаний и наличие файлов весов. При обычном запуске `regime_study` обучение
всех семи вариантов проводится напрямую, и объединение не требуется.

Полная таблица отдельных наблюдений — `results_regime2026/raw_evaluation.csv`,
сводные средние и выборочные отклонения — `results_regime2026/summary.csv`,
параметры и точные контрольные режимы — `metadata.json`; модели сохранены на
каждом срезе обучения. В рукописи **не используется ложная независимость**
восьми проверок одной и той же обученной модели: сначала они усредняются
внутри модели, затем усредняются результаты пяти моделей.

**Ограничения:** пять инициализаций дают описательную, а не окончательную
статистическую проверку малых эффектов. Система, трафик и энергозатраты
синтетические. 

## Структура

- `qmix_aiot/environment.py` — дискретно-событийная модель поступления задач, передачи, очередей, отказов и исполнения.
- `qmix_aiot/learning.py` — рекуррентные локальные сети, монотонная сеть смешивания QMIX, буфер эпизодов, Double Q-learning, Independent DQN и абляции.
- `qmix_aiot/experiments.py` — обучение, повторные эксперименты, сравнение с эвристиками, точное сохранение исходных результатов, измерение времени.
- `qmix_aiot/plots.py` — четыре графика непосредственно по файлам результатов.
- `tests/` — проверки учёта задач, повторяемости, различий сценариев, монотонности и градиентного обновления.
- `qmix_aiot_implementation.py` и `visualizations.py` — входные точки с совместимыми именами.

## Установка и выполнение

Рекомендуется Python 3.12 и виртуальное окружение:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pytest -q
python qmix_aiot_implementation.py --output results --train-episodes 55 --train-seeds 3 --eval-seeds 5 --horizon 90 --eval-horizon 120 --nodes 25 --devices 50
python visualizations.py --results results --figures figs
```

Имеется быстрый технический запуск (не использовать для научных выводов):

```bash
python qmix_aiot_implementation.py --output results-smoke --train-episodes 4 --train-seeds 2 --eval-seeds 2 --horizon 12 --eval-horizon 16 --nodes 4 --devices 8 --without-ablations --inference-repeats 8
```

В основном эксперименте обучаются три независимые модели для каждого нейросетевого метода и выполняются пять проверочных прогонов на модель для каждого сценария. Средние значения метрик сначала агрегируются внутри каждого обучающего запуска, после чего вычисляется среднее и стандартное отклонение между независимыми обученными моделями. Эвристики оцениваются на пяти независимых потоках задач.

## Протокол моделирования

Один шаг означает одну секунду модельного времени. На 50 устройствах заявки возникают как пуассоновский поток с интенсивностью 0,12 задачи/с на устройство. Задача характеризуется объёмом вычислений от 14 до 75 ГОп, требуемой памятью от 1 до 11 ГБ, объёмом передачи от 0,1 до 3 МБ и сроком от 3 до 12 с. Базовая конфигурация содержит 25 узлов с производительностью 25–40 ГОп/с и памятью 24–48 ГБ. Это **допущения синтетической модели, а не измеренные характеристики реального склада**.

У каждого узла одна исполняемая задача, остальные ожидают в очереди. Агент управляет назначением головной задачи своей входной очереди. Действие 0 — отклонение; действия 1...k — назначение узла. Учитываются готовность узла, требуемая память, длительность передачи, ожидаемое время обслуживания и крайний срок задачи. **Прогноз срока строится по опубликованной длине очереди и среднему размеру работы, а не по закрытому содержимому очередей других агентов.** Одновременные решения обрабатываются детерминированно по убыванию приоритета задачи, затем по идентификатору входного узла. При отказе узла его текущая и ожидающие задачи отклоняются.

Проверочные сценарии:

1. `stable` — постоянная интенсивность и без отказов.
2. `peaks` — увеличение интенсивности в 2,6 раза на интервале 25–44 каждого периода длиной 75 шагов.
3. `failures` — отказ 20% узлов между первой и второй третью эпизода, затем восстановление.
4. `heterogeneous` — мощности 15–60 ГОп/с и память 12–64 ГБ при прочих неизменных условиях.

В проверочных запусках используется один и тот же начальный генератор для всех сравниваемых методов; управленческие действия, разумеется, могут приводить к разным траекториям занятости.

## Методики сравнения

| Обозначение | Содержание |
|---|---|
| `adapted_qmix` | Стандартная рекуррентная архитектура QMIX, дополненная предметными наблюдениями, проверкой допустимости действия и специальными слагаемыми награды |
| `vanilla_qmix` | Рекуррентный QMIX без соседских объявлений и предметных добавок к награде; базовая проверка допустимости действий сохранена для честного сравнения |
| `iql` | Независимый Q-оценщик с общими параметрами локальной рекуррентной сети и без QMIX-смесителя (parameter-sharing IQL) |
| `no_public` | Абляция: сохранены награда и маска адаптированного QMIX, но удалены числовые публичные признаки соседних узлов; бинарная маска допустимости по-прежнему несёт косвенную информацию о них |
| `greedy` | Выбор допустимого назначения с минимальным прогнозируемым временем завершения |
| `round_robin` | Циклический выбор среди допустимых узлов |
| `no_gru`, `no_masks`, `no_fairness`, `no_energy` | Абляции по одному компоненту |

Для нейросетевых вариантов используются общие гиперпараметры обучения (55 эпизодов, дисконтация 0,98, Adam 4·10⁻⁴, 3 шага оптимизации после эпизода, минипакет из трёх эпизодов, целевые сети каждые 20 обновлений). Длина обучающего эпизода — 90 шагов; проверочного — 120.

Метрика DCR определяется как 100 × количество завершённых в срок задач / количество поступивших задач. MRT — среднее время ответа **завершённых** задач. TRR включает явные отклонения, сбои и истечение срока в ожидании. Незавершённые к концу эпизода задачи учитываются в знаменателе DCR и отдельно выводятся в `unfinished`. Индекс Джайна вычисляется по накопленным долям обслуживания: `processed_work_i / cpu_capacity_i`, а не по равному числу задач на неодинаковых узлах. Энергетическая переменная — **безразмерный суррогатный показатель объёма вычислений**, не измеренная энергия в джоулях.

## Артефакты эксперимента

`results/raw_evaluation.csv` содержит каждый отдельный запуск; `summary.csv` — средние и выборочные стандартные отклонения; `training_history.csv` — историю обучения; `inference_scaling.csv` — результаты `perf_counter_ns` для 10, 25, 50 и 100 агентов; `metadata.json` — параметры, семена, версию библиотек и характеристики платформы. Дополнительно сохраняются `.pt`-модели.

Измерение масштабируемости относится исключительно ко времени **исполнения** политики на CPU с необученными весами, без симуляции и обучения. Алгоритм не имеет заявленной гарантии сходимости к оптимальной политике. При полном обмене краткими сводками между всеми узлами число взаимодействий растёт как `O(k²)`; число выходов локальных политик равно `k+1`. Нельзя переносить эти эмпирические измерения на асимптотическую сложность всего обучения.

## Ограничения

Это синтетическое исследование: не проведена калибровка на реальном IoT-стенде. Начальные параметры выбраны для проверки методов, а не для утверждения универсальных нормативов качества. Малое число независимых обучающих запусков ограничивает статистическую мощность выводов; `std` — выборочное стандартное отклонение, не доверительный интервал.
